# ADR 0012 — AI provider, privacy, and Silent Router

**Status:** Accepted  
**Date:** 2026-08-27  
**Supersedes:** deferred Phase 2A note that forbade any vendor adapter

## Context

Phase 2A ships a deterministic booking engine and `FakeAIProvider`. Phase 2B adds language understanding only. The backend remains the sole authority for availability, appointments, pricing, identity, and mutations.

Production LLM calls require documented commercial terms, data-use, retention, DPA, subprocessors, and zero-data-retention (ZDR) controls. CI must stay deterministic.

## Decision

### Provider

OpenAI is the recommended first provider. The runtime adapter uses the **Responses API** with **strict JSON Schema Structured Outputs**, Node `fetch` (no vendor SDK until a later license review), and:

- `store=false`
- no tools, no web search, no file search
- no conversations/threads, no `previous_response_id`
- no application-state features
- structured output only

The adapter interface (`AIProvider`, optional `RouteClassifier`) lets orchestrator/domain code switch between Responses and another provider without changing booking rules.

The exact model snapshot is **not** assumed (`gpt-4o-mini` is not the frozen choice). Selection is the first snapshot that passes the frozen Hebrew gold evaluation, starting with an economical classification/NLU model and comparing a stronger snapshot only if intent/entity gates are missed.

CI and default worker runtime stay on `FakeAIProvider`. A real provider is used only when `TAVO_AI_PROVIDER=openai` and secrets are present.

### Prompt privacy

Never send tenant UUID, phone numbers, ciphertext, key material, Meta tokens, raw database rows, or other customers' data. Allowlisted `MinContext` may include timezone, conversation state, and tenant **display names** for active services/staff plus offered option labels already generated by formatters.

### Silent Router

Relationship states: `UNKNOWN`, `BUSINESS_VERIFIED`, `PERSONAL_EXCLUDED`, `HUMAN_ONLY`.

A `customers` row created on first inbound is **not** `BUSINESS_VERIFIED`.

Fail-safe: false negative over false positive. `UNKNOWN` defaults to silence.

Owner override (`PERSONAL_EXCLUDED` / `HUMAN_ONLY` / owner-marked `BUSINESS_VERIFIED`) wins until the owner changes it. Classifier output is never `PERSONAL_*`.

### Deterministic evidence (token/phrase matching)

Business detection must not use naive substring checks (`text.includes('תור')`). Matching uses Unicode NFC, whitespace/punctuation normalization, whole-token and consecutive-phrase matching, valid `HH:mm`, weekday/time phrases, and tenant service/staff name tokens. This is not a full Hebrew morphological analyzer.

Independent signal categories:

- **Booking / business action:** תור, לקבוע, קבע, לבטל, ביטול, להזיז, להקדים, לאחר, מחיר, עולה (and a closed set of explicit surface forms such as התור / תורים / תזיז). **פנוי / זמין** are availability words, not general booking verbs.
- **Service:** tenant-active service names (e.g. תספורת, זקן, תספורת + זקן)
- **Temporal:** היום, מחר, weekday names, בבוקר / בערב, אחרי / לפני, valid HH:mm, closed natural hour phrases
- **Staff:** tenant-active staff display names (plus explicit aliases such as דניאל ↔ Daniel)

Strong combinations that may **allow the current turn** for `UNKNOWN` (not an exhaustive product list, but the rule family):

- booking-action + temporal (`יש תור מחר?`)
- service + temporal (`תספורת מחר בערב`)
- known staff + availability word + temporal (`דניאל פנוי בחמישי?`)
- service + price language (`כמה עולה זקן?`)
- booking-action + service (`תור לתספורת`)
- existing appointment + mutation language

Alone, these are **not** sufficient for `UNKNOWN`: `מחר`, `שבע`, `חמישי`, `איפה אתה`, `יש לך זמן?`.

False-positive traps that must not activate Tavo for `UNKNOWN`: `תוריד את הסרטון`, `אני בתור בסופר`, `דניאל בא לכדורגל?`, `מחיר הדירה עלה`, `מחר?`.

A mid-flow 2A conversation (`state <> IDLE`) may continue the current booking session without promoting the contact.

### Activation is not permanent trust

- Owner / Tier-A deterministic evidence may persist `BUSINESS_VERIFIED` (appointment lifecycle, successful booking/reschedule, explicit owner marking, other documented Tier-A events).
- A lexical Tier-B match may allow **this turn only**. It must not persist `BUSINESS_VERIFIED`.
- Classifier `BUSINESS` may allow **this turn only**. It must not persist `BUSINESS_VERIFIED` in Phase 2B v1.
- Classifier is optional and off by default; it may be invoked only for restricted incomplete business evidence (not temporal-only, not staff-only, not empty).

### Frozen router gates

- Owner PERSONAL override violations = 0
- Obvious-personal false activation = 0
- Ambiguous/personal false activation ≤ 1%, target 0
- `UNKNOWN` defaults to SILENCE

## Consequences

Phase 2A formatters remain the only customer-visible facts. Payments, dashboard, and mixed personal/business production WhatsApp numbers stay out of scope. Demo/test traffic only.
